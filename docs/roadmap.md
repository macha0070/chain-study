## 発展課題（実装済みフェーズの穴を塞ぐ）

実装した攻撃には、対策をわざと入れていない。塞ぐところまでが 1 セット。

### 課題 1 — RFC 6979（決定的 ECDSA）で nonce 事故を根絶する

`ecdsa.sign()` の `k` は `os.urandom` に依存している。乱数源が壊れれば終わり。
RFC 6979 は `k` を秘密鍵とメッセージから HMAC-SHA256 で決定的に導出する。

    k = HMAC_DRBG(key=d, msg=z)

同じ `(d, z)` なら常に同じ `k`、違う `z` なら違う `k`。乱数を使わないので壊れようがない。

**到達判定**
- 同じ鍵・同じメッセージに 2 回署名して、`(r, s)` が完全に一致する
- 違うメッセージなら `r` が必ず違う
- `recover_from_nonce_reuse` を仕掛けても、`r` が一致しないので使えない
- RFC 6979 の Appendix A.2.5（P-256 のテストベクタ）と一致する

参考: RFC 6979 §3.2

---

### 課題 2 — マークル木の CVE-2012-2459 を塞ぐ

`merkle.merkle_root()` は奇数段で最後を複製する。`[a,b,c]` と `[a,b,c,c]` の根が一致する。

対策は 2 通りある。両方書いて比べる。

1. **重複段の拒否** — Bitcoin Core が取った対策。段の中に隣り合う同一ハッシュが
   あったら invalid とする。後付けの対症療法。
2. **ドメイン分離** — RFC 6962 (Certificate Transparency) の方式。
   葉は `H(0x00 || leaf)`、内部ノードは `H(0x01 || left || right)` と、
   ハッシュの入力空間を分ける。そもそも構造の取り違えが起きない。

**到達判定**
- 対策後に `root([a,b,c]) != root([a,b,c,c])` になる
- 既存の `self_check()` の包含証明テストが全部通ったまま
- 2 方式の違いを 3 行で説明できる（どちらが「原因」を消しているか）

参考: CVE-2012-2459 / RFC 6962 §2.1

### 課題 3 — 難易度の自動調整

いまは `difficulty` を固定している。実際のチェーンはブロック生成間隔を一定に保つよう
定期的に難易度を再計算する（Bitcoin は 2016 ブロックごと、目標 10 分）。

    新難易度 = 旧難易度 * (実際にかかった時間 / 目標時間)

ただし PoW の難易度はビット数なので、対数で効くことに注意。

**到達判定**
- マイナーの数（= ハッシュ力）をシミュレートで 2 倍にすると、難易度が約 1 ビット上がる
- 調整後、ブロック生成間隔の移動平均が目標値に戻る様子をグラフか数列で出せる
- 調整幅に上限（Bitcoin は 4 倍）を入れないと何が起きるか、実験で示せる

---

### 課題 4 — タイムスタンプ検証

`block.py` はタイムスタンプを検証していない。攻撃者が未来や過去の値を入れると
難易度調整を操作できる（time warp 攻撃）。

**到達判定**
- 「直近 11 ブロックの中央値より後」「ネットワーク時刻 +2 時間より前」の 2 条件を実装
- 偽のタイムスタンプで難易度を不当に下げる攻撃を、対策前に成功させ、対策後に失敗させる

## Phase 8 — P2P とノード間の伝播 ✅ 実装済み

`chain/node.py`。ノードごとに `Blockchain` と mempool を持ち、遅延つきの配送キューで
ブロックと tx を伝播させる。分岐は意図的に作るものではなく、遅延の帰結として起きる。

実測できたこと:

| 遅延 / ブロック間隔 | 孤児率 |
|---|---|
| 0% | 0.0% |
| 5% | 0.0% |
| 10% | 4.9% |
| 25% | 16.4% |
| 50% | 31.1% |
| 100% | 44.3% |

Bitcoin がブロック間隔を 10 分に置いている理由がこの表に出ている。
伝播が数秒なら比は 1% 以下で、孤児は無視できる。

**残っている課題**

- ノードごとに接続を制限する（いまは全ノードが全ノードと直結している完全グラフ）。
  現実のトポロジは疎で、その場合は伝播が「ホップ数 × 遅延」になる。
  → 到達判定: 接続数を 8 に制限したとき、孤児率が完全グラフより悪化することを示す
- **eclipse 攻撃**: 特定ノードの接続を攻撃者だけで埋め、そのノードに偽の世界を見せる。
  → 到達判定: 被害ノードだけが別の tip を信じ続ける状態を作れる
- tx の伝播を Compact Blocks 相当にして、伝播量を減らす

## Phase 9 — スクリプト / 検証言語

いまの UTXO のロック条件は「このアドレスの鍵で署名せよ」に固定されている。
Bitcoin はここにスタックベースの小さな言語を置いた。

やること:
- スタックマシン（`OP_DUP`, `OP_HASH160`, `OP_EQUALVERIFY`, `OP_CHECKSIG`）
- P2PKH（いまの挙動をスクリプトで書き直す）
- **マルチシグ** `OP_CHECKMULTISIG` — m-of-n
- **タイムロック** `OP_CHECKLOCKTIMEVERIFY`

**到達判定**
- いまの送金が、スクリプト解釈系の上で同じように動く
- 2-of-3 マルチシグで、鍵 1 本では使えず 2 本で使えることを確認できる
- ループがないこと（チューリング不完全）が何を保証しているか説明できる

## Phase 10 — アカウントモデルと状態遷移（Ethereum 方向）

UTXO ではなく「アドレス → 残高」の辞書を状態とするモデル。
`D:\IBE\blockchain-study` の Solidity 側と繋がるのはここ。

やること:
- 状態を `dict[address, (nonce, balance)]` にする
- リプレイ攻撃を nonce で防ぐ（UTXO では構造上起きなかった問題）
- ガス（実行費用）の概念を入れる

**到達判定**
- 同じ署名済み tx を 2 回投げると、2 回目が nonce で弾かれる
- UTXO モデルとアカウントモデルで、並列検証しやすさの違いを説明できる

## ★ Proof of Stake と finality

PoW は「確定が確率的」だった。PoS + BFT 系のプロトコルは **finality**、
つまり「もう覆らない」という状態を作れる。何を代償に払っているのか。

やること:
- 単純な PoS（保有量に比例して提案者を選ぶ）を実装し、nothing-at-stake 問題を再現する
- Casper FFG のような 2/3 投票による finality を入れる
- スラッシング（不正提案の罰）で nothing-at-stake が消えることを確認する

**到達判定**
- PoS 単体では、攻撃者が全ての枝に無償で賭けられることを実験で示せる
- スラッシング導入後、その戦略が損になることを数字で示せる
- 「PoW は物理的コスト、PoS は経済的な人質」という違いを自分の言葉で説明できる

## 暗号側の発展（selfproject / ibe-study との接続）

このリポジトリは Phase 2 で楕円曲線を書いた。ibe-study の Phase 1 が実質ここで埋まった。
そこから先は 2 つの方向に分かれる。

- **Schnorr 署名 → MuSig → Taproot**
  ECDSA より素直な署名。線形性があるので鍵と署名を足し合わせられる。
  Bitcoin は 2021 年に Taproot でこちらへ移った。
  → ibe-study Phase 2（ペアリング）に入る前の良い足がかり。

- **ゼロ知識証明 → zk-Rollup**
  「知っていることを、内容を明かさずに示す」。
  Schnorr の対話証明 → Fiat-Shamir 変換 → R1CS → zkSNARK の順。
  Phase 0 の有限体と Phase 2 の楕円曲線がそのまま土台になる。

- **SHA-256 の自作**
  このリポジトリで唯一 `hashlib` に頼っている部分。
  圧縮関数を書くと、長さ拡張攻撃がなぜ起きるか（と `dH` がなぜ 2 段掛けか）が腑に落ちる。

## Web UI とインフラの課題

`web/server.py` + `web/static/`。`http.server` だけで書いてある。

- **状態が消える**。プロセスを落とすとチェーンも消える。
  ブロックを追記専用ファイルに書き出し、起動時に読み直す。
  → 到達判定: コンテナを再起動しても高さと UTXO 集合が一致する
  → ついでに「チェーンは追記専用ログである」が実装として腑に落ちる
- **ポーリングをやめる**。いまは UI が 0.35〜2.5 秒ごとに `/api/state` を読んでいる。
  Server-Sent Events にすればブロックが着いた瞬間に描ける。
  → 到達判定: 採掘中のログが遅延なく流れる
- **複数コンテナで本当に分散させる**。いまの P2P は 1 プロセス内の模擬。
  compose で 4 コンテナ立て、TCP でブロックを配ってみる。
  → 到達判定: `docker compose up --scale node=4` で自然な分岐が起きる
  → ここまでやると「模擬」の但し書きが消せる
